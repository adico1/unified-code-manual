# Unified Code — Goals and Boundaries

This document is the canonical navigation map for the Unified Code objective.
It separates destination from evidence and keeps implementation contracts in
their dedicated specifications.

Status meanings:

- **PROVEN** — implemented and reproducibly verified in this repository.
- **PARTIAL** — a bounded implementation exists, but the complete law is not
  yet satisfied.
- **OPEN** — required architecture or proof is not yet implemented.
- **RESEARCH** — a hypothesis or interpretation that requires independent
  evidence.

## Main goal

**PARTIAL**

Create one unified construction language in which one canonical authority can
manifest a complete, exact and verified Thing:

```text
human intention
→ canonical name and request
→ complete seed program
→ deterministic build-time assembly
→ exact specialized application
→ every selected interface
→ generated evidence
→ atomic installation
→ execution
```

The final root proof applies the same law to the creator:

```text
ROOT.seed
→ compiler
→ framework
→ UEM
→ independent Python and C hosts
→ applications and interfaces
→ tests, mutations and documentation
→ complete repository
→ byte-identical fixed point
```

The objective is not merely source generation. The seed must be the complete
application program; the creator must contribute construction law without
containing application meaning; and the generated result must contain neither
excess nor omission.

## Inner boundaries

The application body has seven explicit responsibilities:

| Stage | Boundary responsibility |
| ---: | --- |
| 1 | Outer input → inner input: parse and normalize a physical request. |
| 2 | Inner input → core input: select the exact canonical computation values. |
| 3 | Core preparation: establish validated inputs, constants and parameters. |
| 4 | Core processing: execute the selected computation or state transition. |
| 5 | Core collection: construct result, state, error and ordered evidence. |
| 6 | Core output → inner output: remove core-specific representation. |
| 7 | Inner output → outer output: render the selected physical projection. |

Stages 1–3 move inward toward the computation center. Stages 5–7 move
outward toward manifestation. Stage 4 is the shared center.

## Outer boundaries

An outer boundary joins the canonical system to an authority or substrate it
does not control. Every effect must be named and audited.

| Boundary | Inward responsibility | Outward responsibility |
| --- | --- | --- |
| Human | Receive an explicit request or event. | Present a result or request confirmation. |
| Name registry | Receive a qualified identity and pinned snapshot. | Return an exact record or explicit unresolved outcome. |
| Seed storage | Read a pinned canonical authority. | Publish a new authorized seed revision. |
| GUI | Receive keyboard, pointer and window events. | Render declared controls, state and errors. |
| CLI | Receive arguments or standard input. | Emit canonical output and exit status. |
| Browser | Receive DOM and browser events. | Render HTML, canvas and accessible output. |
| Filesystem | Read an authorized resource. | Atomically write or replace an authorized resource. |
| Persistence | Load explicit application state. | Persist state only through `OUTWARD`. |
| Network | Receive an authorized protocol message. | Send an authorized protocol message. |
| AI | Receive an explicit AI result. | Send only a user-authorized request. |
| Git/GitHub | Observe repository and collaboration state. | Mutate branches, PRs or issues only through an authorized action. |
| Clock/scheduler | Receive measured time, event or tick coordinates. | Request scheduling through a declared host contract. |
| Foreign core | Convert canonical input into foreign input. | Convert foreign output or failure back into canonical data. |
| UEM host | Admit canonical bytecode and physical effects. | Return canonical machine result and evidence. |
| Installation | Inspect the previous valid tree. | Atomically expose a completely verified replacement. |
| Publication | Resolve a verified artifact and destination. | Publish only the exact verified identity. |
| Hardware | Receive physical signals through a host adapter. | Produce physical effects through that adapter. |

## Boundaries that must never collapse

| Separation | Law |
| --- | --- |
| Potential / manifestation | A name addresses potential; it does not hide application behavior. |
| `בלי_מה` / `מה` | Permanent construction truths remain separate from selected application meaning. |
| Pre-bootstrap / post-bootstrap | The minimal trusted substrate is distinct from the generated unified language. |
| Seed / generated output | Generated files never become independent application authority. |
| Creator / application | The generic creator contains no application vocabulary or branches. |
| Artifact / deployment | One content-addressed artifact may have zero, one or many installations. |
| Build / compile / install / execute | Each lifecycle phase has its own inputs, outputs and evidence. |
| Semantic structure / audit evidence | Deterministic meaning is hashed separately from host paths, timing and environment measurements. |
| Canonical Thing state / domain status | `valid` is not `resolved`, `active`, `completed` or another domain outcome. |
| Expected / unhandled failure | Expected validation creates no ticket; an unhandled failure follows redaction and deduplication policy. |
| Watcher / verifier / creator / boundary | A watcher observes, a verifier judges, a creator generates and a boundary manifests. |
| Projection / root fixed point | One stable interface does not prove convergence of the shared authority and every projection. |
| Native / foreign core | Foreign representation and failures cannot escape the generated adapter. |
| Python / C hosts | Hosts remain independent while implementing one pinned UEM surface. |
| Manual experiment / accepted standard | Discovery remains distinguishable from verified governing law. |
| Proven / partial / open / research | Ambition never substitutes for measured evidence. |

## Governing stopping law

Application-level completion requires an exact seed, deterministic generated
tree, passing acceptance, isolated runtime, atomic installation and resolved
ten-depth evidence.

Root completion requires more:

```text
exactly ten semantic depths
∧ one pinned canonical authority
∧ every authoritative input identified and hashed
∧ every watcher resolved
∧ every projection converged
∧ no missing, foreign, duplicate, misplaced or unresolved letter
∧ no independently authored projection
∧ no unauthorized handwritten source
∧ successor generation changes zero bytes
→ בלימה
→ גילה
```

Until that root fixed point is measured, application convergence is evidence
toward the main goal, not completion of it.
